# Next Steps — Resolving the Two Launch Blockers

Execution doc for a single agent (or one per step). Follow the steps **in order**.
After each step: rebuild (production), install, and check the specific symptom
before moving on. Do NOT stack multiple fixes into one rebuild.

Two symptoms, tracked separately but suspected to share one webview-layer root:

- **A (spinner):** stuck on "Opening Nabu" — backend returned the vault path but
  the frontend never transitioned.
- **B (fixed box):** window/webview pinned at ~1280×800; gray native background
  shows around it when enlarged.

---

## Unified hypothesis (from audits A + B + references)

**A Tauri 2.11.5 macOS WKWebView regression**: after the wasm/Dioxus boots and
takes over, the webview (a) stops delivering async messages — so
`eval_with_callback` callbacks and IPC Promise resolutions never fire (Symptom A)
— and (b) reports a fixed intrinsic content size that pins the window at ~1280
(Symptom B). One broken webview state, two symptoms.

Supporting evidence:
- Audit A: `eval_with_callback` works *before* wasm boots, then callbacks go
  silent *after* (call returns `Ok(())`, callback never invoked). Backend
  received + returned `check_vault_exists`, frontend never transitioned.
- Audit B: webview measured exactly at window size at boot, but
  `set_size(1700,1100)` was clamped back to 1280 wide → size is constrained.
- References: working apps use **older Tauri** (mtc 2.5.1, maes 2.9.3) and
  **Dioxus 0.7**; Nabu is the outlier on Tauri 2.11.5 + Dioxus 0.6.3.

---

## Step 0 — Confirm the webview message path (cheap, do first)

Replace the `eval_with_callback` poller with **synchronous `window.eval()`** for
post-wasm probes.

- Touchpoint: `src-tauri/src/lib.rs`, the `on_page_load` poller task.
- Change: instead of `eval_with_callback(...)` (fire-and-forget callback), call
  `window.eval("JSON.stringify((window.__nabuLogs||[]).splice(0))")` which returns
  the string synchronously, and log it directly.
- Also call `window.eval("1+1")` post-wasm and log the result.
- Read: if sync `eval` returns values post-wasm → the *callback/async* path
  specifically is broken → confirms a Tauri bridge bug → proceed to Step 1.
  If sync `eval` also returns nothing → the webview JS engine is stalled →
  stronger signal to jump to Step 4 (upgrade/downgrade Tauri).

## Step 1 — Replicate mtc's post-build window re-assert  [highest likelihood]

From `mtc-app/src/lib.rs` (a working Tauri+Dioxus app), the window is explicitly
made resizable + sized *after* creation. Replicate in Nabu's setup.

- Touchpoint: `src-tauri/src/lib.rs`, in `.setup()` — the block that currently
  does `app.get_webview_window("main")`.
- After retrieving the `main` webview window, add:
  - `window.set_resizable(true)?;`
  - `window.set_min_size(Some(PhysicalSize { width: 640, height: 600 }))?;`
  - `window.set_size(PhysicalSize { width: 1280, height: 800 })?;` (re-assert,
    then let the user grow it)
- Keep `tauri.conf.json` `resizable:true`. Do NOT call `maximize()` automatically
  (Nabu is a normal window; mtc's `maximize()` was its own default).
- Verify: Symptom B — drag the window edge; the black box should now track.
- Import needed: `tauri::PhysicalSize`.

## Step 2 — Swap `100vh/100vw` → `100dvh/100dvw`  [low cost, matches maes]

- Touchpoint: `src/styles/app.css` — `.app` (`app.css:238`) and `html,body`
  (`app.css:162`): change `100vw/100vh` → `100dvw/100dvh`.
- Touchpoint: `crates/nabu-ui/src/components/app.rs` Loading screen (:120) and
  `vault_setup_wizard.rs` root (:29): change `h-screen w-screen` →
  `h-dvw w-dvh` (Tailwind equivalents of `100dvw/100dvh`).
- Rebuild via `npm run css:build` (part of `cargo tauri build`). Verify
  `dist/generated/tailwind.css` contains the `dvh/dvw` rules.
- Verify: Symptom B still.

## Step 3 — Swap to the official Dioxus CLI (`dx bundle`)  [structural]

Nabu hand-rolls `src-tauri/scripts/build-dioxus.sh` (custom index.html + `#main`
+ boot-splash). The references use `dx bundle`, which generates a known-good
mount page.

- Touchpoint: `src-tauri/tauri.conf.json` `build.beforeBuildCommand` →
  `dx bundle --release --package nabu-ui` and set `frontendDist` to the
  `dx` output dir (see maes: `../target/dx/aide_ui/release/web/public`).
- Touchpoint: remove reliance on `build-dioxus.sh` (keep as fallback).
- Requires: `dx` (Dioxus CLI) installed; confirm it can build the `nabu-ui`
  workspace (it was bypassed before because a transitive git2/auth-git2 tree
  did not compile — re-check on current toolchain).
- Verify: app boots past the loading screen; `#main` mount is generated by dx.

## Step 4 — Align dependency versions  [if Steps 1–3 don't resolve]

Working references use Tauri 2.9.3 + Dioxus 0.7. Nabu is Tauri 2.11.5 + Dioxus
0.6.3.

- Try **Tauri 2.11.5 → 2.9.3** first (cheap: version bump in
  `src-tauri/Cargo.toml` + `cargo update` + rebuild). Highest likelihood if the
  regression is in 2.11.5.
- Then consider **Dioxus 0.6.3 → 0.7** (matches references; larger migration —
  `rsx!`/API changes). Do this only if the Tauri bump alone is inconclusive.

## Build / verify loop (every step)

```bash
# production only — never cargo build (dev-mode → white/black screen)
cd src-tauri && cargo tauri build
rm -rf /Applications/Nabu.app && cp -R target/release/bundle/macos/Nabu.app /Applications/Nabu.app
pkill -f "Nabu.app/Contents/MacOS/app"
nohup "/Applications/Nabu.app/Contents/MacOS/app" > /tmp/nabu.log 2>&1 &
# human tests: does it pass Loading? does the window resize?
grep -E "\[RESIZE\]|\[WEB\]|\[WEBVIEW\]|\[setup\]|panic" /tmp/nabu.log
```

## Definition of done
- Symptom A: app leaves the "Opening Nabu" screen (reaches wizard or workspace).
- Symptom B: dragging the window edge grows the black box with it (no gray gap).
- No stale-instance confusion: always `pkill` before relaunch.
